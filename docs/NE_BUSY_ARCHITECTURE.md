# НЕ БУСЫ: Архитектура Скрытого Перехода

Статус: концепт архитектуры Nando Wave / LLMWave.

Главная мысль:

```text
не next-token prediction
не lookup
не cache
не ручное правило

а

скрытое состояние
  + компактный центр повторяемого перехода
    + verifier
      -> проверяемое действие
```

Это не набор известных "бусинок". Смысл архитектуры в том, что действие возникает как компактный центр повторяемого перехода.

## 1. Базовая Формула

```text
state_t + operator/action -> state_t+1
```

В скрытом виде:

```text
z_t + operator_center -> z_t+1
```

Где:

```text
z_t
  скрытое состояние ситуации

operator_center
  фазовый центр / центр масс повторяемого перехода

z_t+1
  следующее состояние после действия

verifier
  проверяющий, который не даёт галлюцинации стать действием
```

## 2. Слои

```text
ВХОД
  |
  +-- текст
  +-- tool event
  +-- код
  +-- команда
  +-- состояние среды
  +-- видео / сенсорный поток
      |
      v

L1: Surface Layer
  |
  +-- видит поверхность:
  |     n-grams
  |     токены
  |     команды
  |     cursor/state
  |     tool output shape
  |
  v

L2: Hidden State Layer
  |
  +-- собирает скрытые признаки:
  |     тип ситуации
  |     роли
  |     слоты
  |     условия
  |     наблюдаемый state
  |     action atoms
  |     result atoms
  |
  v

L3: Phase-Center Operator Layer
  |
  +-- не хранит готовый ответ
  +-- не хранит lookup
  +-- учит компактный центр перехода:
  |
  |       state_t + action -> state_t+1
  |
  +-- correct должен быть ближе wrong
  +-- высокий margin даёт кандидат на CPU
  |
  v

L4: Streaming Selector / Goal-State Layer
  |
  +-- выбирает:
  |     какой класс разрезать
  |     какой оператор держать горячим
  |     какой оператор выкинуть
  |     где риск false_accept
  |     где экономия
  |     где нужен fallback
  |
  +-- управляет операторной памятью
  |
  v

VERIFIER
  |
  +-- проверяет результат без LLM:
  |     совпало?
  |     безопасно?
  |     не lookup?
  |     false_accepts = 0?
  |
  v

ACTION
  |
  +-- CPU accept
  +-- или fallback к большой LLM
```

## 3. Чем Это Отличается От Обычной LLM

Обычная LLM:

```text
контекст
  -> следующий токен
    -> следующий токен
      -> следующий токен
```

Nando / НЕ БУСЫ:

```text
ситуация
  -> скрытое состояние
    -> переносимый оператор
      -> проверенный переход
```

Обычная LLM в основном продолжает текст.

Nando должен строить память проверенных действий.

## 4. Чем Это Отличается От Cache / Lookup

Cache:

```text
такой же запрос уже был?
  -> вернуть тот же ответ
```

Lookup:

```text
ключ найден?
  -> взять готовое значение
```

Phase-center operator:

```text
новая ситуация похожа по переходу?
  -> применить компактный оператор действия
  -> проверить результат
```

То есть cache помнит прошлый ответ.

Оператор переносит действие на новую ситуацию.

## 5. Как Оператор Возникает

```text
поток опыта
  |
  +-- много похожих переходов
      |
      +-- extract state/action/result
          |
          +-- phase vectors
              |
              +-- центр масс перехода
                  |
                  +-- negatives / wrong / background
                      |
                      +-- verifier
                          |
                          +-- переносимый CPU operator
```

Главное:

```text
оператор не задаётся руками
оператор не является answer table
оператор возникает как центр повторяемого перехода
```

## 6. Сравнение С JEPA

JEPA-подход:

```text
текущее скрытое состояние
  + действие
    -> предсказанное будущее скрытое состояние
```

Nando-подход:

```text
скрытое состояние / phase atoms
  + phase-center operator
    -> проверяемый переход
      -> accept или fallback
```

Гибридная идея:

```text
JEPA даёт скрытое состояние мира
Nando даёт проверяемый переносимый оператор перехода
```

## 7. Почему Нужен L4

L3 умеет оценивать оператор.

Но L3 не должен один решать всю экономику, риск и стратегию.

L4 нужен как слой управления:

```text
L4
  |
  +-- ищет жирные классы в потоке
  +-- режет широкий класс на безопасные подцентры
  +-- выбирает marginal value, а не красивый bucket
  +-- учитывает exact cache overlap
  +-- учитывает false_accept risk
  +-- решает, что держать в hot memory
  +-- отправляет опасное в fallback
```

Формула L4:

```text
выбирать не самый жадный оператор
а самый выгодный среди безопасных
```

## 8. Операторная Память

Память должна быть не плоской таблицей ответов, а набором центров переходов:

```text
operator memory
  |
  +-- hot centers
  |     +-- маленькие
  |     +-- быстрые
  |     +-- verifier-bound
  |
  +-- quarantine centers
  |     +-- найдены
  |     +-- ещё не безопасны
  |
  +-- cold archive
        +-- история
        +-- evidence
        +-- rejected candidates
```

Hot path:

```text
event -> phase vector -> score -> accept/fallback
```

Cold path:

```text
trace -> mining -> split -> verifier -> quarantine -> promotion
```

Hot path не должен тащить:

```text
JSONL
отчёты
компиляцию
provider billing
heavy mining
ручной class list
```

## 9. Запреты

Запрещено считать архитектурным успехом:

```text
lookup
target_id
proof_rule_id authority
concrete_x_lookup
manual local_out_t
ручной hardcode агента
source-specific branch как generic core
local accept без verifier
local accept при false_accepts > 0
synthetic savings как рыночный claim
```

## 10. Что Значит "НЕ БУСЫ"

Бусы:

```text
взяли cache
взяли classifier
взяли rule engine
взяли prompt trick
связали ниткой
```

НЕ БУСЫ:

```text
поток опыта
  -> скрытые состояния
    -> центры переходов
      -> проверяемые операторы
        -> CPU/runtime память действий
```

Коротко:

```text
L1 видит поверхность
L2 собирает скрытое состояние
L3 переносит действие через phase-center
L4 выбирает и управляет операторной памятью
Verifier не даёт соврать
```

## 11. Где Применима Такая Архитектура

Главное условие:

```text
есть повторяемый переход состояния
и результат можно проверить
```

Базовая форма:

```text
state_before + action -> state_after
```

Если переход повторяется, переносится и проверяется, это зона Nando.

| Область | Что является состоянием | Что делает оператор | Почему Nando подходит |
|---|---|---|---|
| AI agents / Codex-like | проект, файлы, stdout, git status | продолжает шаг агента | много повторяемых действий, можно проверять |
| LLM API cost saving | запросы, ответы, tool calls | заменяет часть LLM-вызовов CPU | экономия токенов и денег |
| IDE / coding tools | код, cursor, diff, тесты | rename, patch, parse error, fix pattern | результат проверяется компилятором и тестами |
| DevOps / CI | логи, статусы, failed jobs | классифицирует и предлагает ремонт | много шаблонных инцидентов |
| Support / CRM | тикет, статус, история клиента | route, classify, draft action | повторяемые workflow |
| Документооборот | поля, статусы, формы | extract, normalize, validate | verifier простой |
| Compliance / audit | документы, правила, события | проверяет переход статуса | важна доказуемость |
| Робототехника | сенсоры, поза, команда | выполняет проверенное действие | маленький CPU runtime |
| Edge / IoT | локальное состояние устройства | принимает локальное решение без облака | дешево, быстро, offline |
| Обучаемая память | поток опыта | находит новый оператор | можно самообучаться из trace |

Самые сильные первые рынки:

```text
1. AI coding / agents
   |
   +-- уже есть trace
   +-- есть tool calls
   +-- есть stdout
   +-- есть git / тесты / diff
   +-- много проверяемых действий

2. LLM gateway / cache layer
   |
   +-- cache ловит только точные повторы
   +-- Nando может ловить переносимые действия
   +-- позиция: verified action compression поверх cache

3. DevOps / CI automation
   |
   +-- ошибки повторяются
   +-- логи структурны
   +-- verifier часто простой

4. Документооборот / workflow
   |
   +-- много переходов:
   |     received -> checked
   |     checked -> approved
   |     checked -> rejected
   |
   +-- можно проверять поля, статусы и правила

5. Edge robotics / embedded repeat-action
   |
   +-- маленький оператор
   +-- дешёвый CPU
   +-- проверенное действие
   +-- можно работать без большой LLM
```

Коротко:

```text
Nando применим там,
где "думание" можно представить
как проверяемый переход состояния.
```

## 12. Северная Звезда

Построить модель, которая:

```text
читает поток опыта
находит повторяемые переходы
сжимает их в компактные операторы
проверяет их без большой LLM
исполняет безопасные действия на CPU
отправляет новое и опасное в fallback
```

Это путь от "говорящей модели" к "говорящей и исполняющей модели".

Не просто модель, которая пишет ответ.

А модель, у которой появляется память проверенных переносимых действий.
