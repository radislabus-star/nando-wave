# Nando Wave: потоковый самообучающийся майнер V3

Дата фиксации: 2026-07-15

## 1. Конечная цель

Автоматически превращать повторяемые конструкции живого трафика в компактные
типизированные программы, которые исполняются на процессоре и допускаются только
после независимой проверки.

Конечный коммерческий барьер:

```text
доля обычного трафика, обработанного на процессоре >= 50%
экономия входных токенов                         >= 50%
ложные разрешения                                = 0
расхождения исполнения и проверки                = 0
покрытие квитанциями независимой проверки         = 100%
жёсткий экономический барьер                      = PASS
Product M3                                       = PASS
```

Текущая подтверждённая отправная точка:

```text
обычные запросы                                  1 263
проверенные локальные ответы                        29
сэкономленные входные токены                41 392 477
все входные токены                         3 393 905 152
экономия входных токенов                          1,2%
ложные разрешения                                    0
расхождения исполнения и проверки                    0
```

## 2. Неизменяемые правила

1. Производственный путь реализуется на Rust. Python в нём запрещён.
2. Обучение видит завершённую трассу и фактический ответ как учебную метку.
3. Исполнение никогда не видит фактический будущий ответ или действие.
4. Волновой механизм ранжирует поиск, но не выдаёт право на исполнение.
5. Типизированная программа исполняет ответ.
6. Независимый проверяющий отдельно воспроизводит результат.
7. При неоднозначности система возвращает `ABSTAIN` и отправляет запрос в LLM.
8. Майнер не выдаёт себе право на исполнение. Это делает внешний контроллер допуска.
9. Будущие данные не фабрикуются и не переносятся из обучающего окна.
10. В коммерческую экономию входят только реально предотвращённые вызовы с квитанцией.
11. Горячий путь не читает гигабайтные журналы и не выполняет полный повтор истории.
12. Все очереди ограничены; давление назад явно учитывается в отчёте.
13. Имена функций и полей разрешены как учебные подсказки, но не как единственное
    основание исполняющего решения.

## 4. Этап 1. Каноническая завершённая трасса

### Задача

Перестать считать внутренний JSONL Codex единственным смысловым источником.
Сделать единый тип события, который может наполняться как сетевым шлюзом, так и
адаптером локального журнала.

### Изменения

- Ввести `CanonicalTurnEvent`:
  - начало хода;
  - запрос пользователя;
  - вызов инструмента;
  - результат инструмента;
  - итоговый ответ;
  - итоговое действие;
  - учёт токенов;
  - явное завершение.
- Ввести `CompletedTurn` с двумя физически разделёнными частями:
  - `RuntimeView`: только данные, доступные до решения;
  - `TeacherView`: фактический ответ, действие и результат завершённой трассы.
- Завершать ход при выполнении условий:
  - получен итоговый ответ или итоговое действие;
  - все начатые обязательные вызовы имеют результат либо явно продолжаются;
  - нет незакрытой неоднозначной операции.
- `token_count` использовать для экономики, а не как единственное доказательство
  смыслового завершения.
- Следующий пользовательский ход остаётся аварийной границей, но фиксируется как
  отдельная причина завершения.

### Барьер

```text
один реальный ход -> одна CompletedTurn
повторное чтение -> тот же идентификатор и те же байты
незавершённый вызов -> CompletedTurn не создаётся
TeacherView недоступен через типы исполняющему пути
```

## 5. Этап 2. Структурное описание результата

### Задача

Заменить правило «весь ответ равен одному значению» на точное описание частей
ответа и их происхождения. Вероятностная векторизация не используется.

### Изменения

- Рекурсивно разобрать наблюдения в `ValueGraph`:
  - объект;
  - коллекция;
  - запись;
  - строка;
  - число;
  - логическое значение;
  - `null`;
  - канонический структурный путь.
- Разобрать фактический ответ в `OutputGraph`:
  - текстовые участки;
  - JSON-значения;
  - числа;
  - статусы;
  - коллекции;
  - границы шаблона.
- Найти точные соответствия между `ValueGraph` и `OutputGraph`:
  - прямое равенство;
  - точное вхождение канонического значения в текст;
  - несколько независимых вхождений;
  - тип и кардинальность;
  - принадлежность;
  - порядок;
  - сохранённый контекст.
- Необъяснённые части ответа сохранить, а не выбрасывать всю трассу.
- Если одному участку соответствуют несколько источников, отметить
  неоднозначность и запретить последующий допуск до появления различающего guard.
- Статический текст пропускать через действующую строгую политику приватности.

### Барьер

Следующие ответы должны давать структурные учебные записи:

```text
3
{"status":"ok"}
Selected values: [3, 5].
Успешно: 3, ошибок: 2.
Команда завершена.
```

Полное совпадение, шаблон и несколько источников должны различаться типами, а не
ручными названиями профилей.

## 6. Этап 3. Широкий типизированный язык программ

### Обязательные программы

```text
project(selector)
status(selector, mapping)
count(collection)
filter(collection, predicate)
aggregate(collection, operation)
compose(step...)
render(parts...)
function_call(symbol, arguments)
constant(value)
role_ref(role)
ABSTAIN
```

### Обязательные способы выбора

```text
единственная коллекция
единственное значение заданного типа
значение по структурному пути
поле, связанное точным равенством
элемент по предикату
значение по временному отношению
неизменившийся остаток структуры
```

### Правило развития

Новый примитив добавляется только при наличии значимого объёма реальных
непокрытых токенов, который невозможно объяснить существующей грамматикой.

### Барьер

`project`, `status`, `count`, `filter` и `compose(filter, count)` должны
синтезироваться из данных без новой ветки Rust для конкретной функции или имени поля.

## 7. Этап 4. Самообучение учитель/ученик

### Учитель

После завершения трассы имеет право видеть фактический ответ и действие. Они
используются для:

- широкой группировки повторяющихся переходов;
- определения формы результата;
- построения положительных и конкурирующих отрицательных примеров;
- ранжирования по потенциально экономимым токенам.

### Ученик

Получает только `RuntimeView` и должен воспроизвести `TeacherView` типизированной
программой.

### Группировка

Ключ группы состоит из:

- нормализованной формы учебного результата;
- структурной формы доступных данных;
- типов ролей;
- формы программы;
- без конкретных приватных значений.

Одинаковый переход с переименованными полями остаётся одной группой. Разные
исполняющие программы не сливаются только из-за похожего текста.

### Барьер

```text
число мелких групп не растёт пропорционально числу поверхностей
teacher label используется при обучении
teacher label отсутствует в runtime package
глобальные конкурирующие действия присутствуют среди negatives
```

## 8. Этап 5. Волновое ранжирование

Волновая память ранжирует:

- связи источника и результата;
- назначения ролей;
- способы выбора;
- скелеты программ;
- порядок композиции;
- различающие отрицательные центры.

Сравниваются режимы:

```text
полная фаза
без фазы
перемешанная фаза
случайный центр
без отрицательного центра
```

### Барьер

Полная фаза находит ту же правильную программу с нулём ошибок, но проверяет
существенно меньше AST, чем режим без фазы. Нулевое покрытие считается провалом.

## 9. Этап 6. Настоящее исправление по контрпримерам

### Цикл

```text
гипотеза
-> повтор положительных примеров
-> жёсткие отрицательные примеры
-> контрпример
-> определить причину
-> изменить программу, selector, guard или группу
-> повторить
```

### Допустимые исправления

- заменить источник значения;
- уточнить способ выбора;
- добавить проверяемое условие применимости;
- изменить шаблон результата;
- добавить шаг композиции;
- создать подцентр;
- разделить смешанную группу;
- полностью отказаться от гипотезы.

Простое удаление кандидата без создания улучшенной гипотезы не считается полным
циклом исправления.

### Целевая функция

```text
ложные разрешения = 0
+ максимальное покрытие токенов будущего окна
+ максимальное число предотвращённых вызовов
+ полное покрытие независимой проверкой
- размер программы
- число точных проверок
- стоимость поиска
```

## 10. Этап 7. Поддержка, будущее окно и перезапуск

- Поддержка и будущее окно разделяются по времени события до синтеза.
- Сессии и intent не могут одновременно попасть в оба окна.
- Точные runtime-примеры, необходимые для parity, сохраняются в bounded CBOR.
- После перезапуска доказательство восстанавливается без полного повтора истории.
- Повтор события определяется каноническим идентификатором, а не смещением файла.
- Конфликт одинаковых идентификаторов блокирует пакет.

### Барьер

```text
support rows >= 32
future rows >= 32
future sessions >= 3
wrong accepts = 0
runtime parity failures = 0
missing receipts = 0
exact-cache overlap = 0
restart сохраняет parity authority
```

## 11. Этап 8. Поточный и компактный Rust-контур

- Убрать неограниченную очередь файловых уведомлений.
- Применить ограниченный канал с объединением повторных уведомлений одного файла.
- Каждое событие обрабатывается один раз.
- Старое доказательство переиспользуется по хешу зависимости.
- Полный повтор истории не выполняется на каждом цикле.
- Checkpoint записывается атомарно и только при изменении поколения.
- Горячий реестр содержит только центры, guards, bytecode и verifier metadata.
- Большие учебные reservoirs не загружаются в serving hot path.
- Отчёт показывает время каждого этапа, очередь, память и число переиспользований.

### Бюджеты первой рабочей версии

```text
idle CPU                                      < 1% одного ядра
горячий ACTIVE registry                       < 4 MiB
Wave routing state                            < 4 MiB
очередь событий                               bounded
полный исторический повтор при обычном старте 0
время маршрутизации p99                       < 250 мкс
```

## 12. Этап 9. Внешний допуск и исполнение

Майнер публикует неизменяемый пакет-кандидат. Отдельный Rust-контроллер проверяет:

- разделение поддержки и будущего окна;
- квитанции независимого проверяющего;
- причинный вклад Wave;
- runtime parity;
- отсутствие lookup/cache leakage;
- приватность шаблонов;
- бюджеты;
- fallback;
- срок действия доказательств.

Только после этого пакет получает authority. Исполняющий путь использует только
`RuntimeView`.

## 13. Этап 10. Отчёт и коммерческий учёт

Единый русский отчёт должен показывать:

```text
все обычные запросы и токены
сколько трасс завершено
сколько отклонено на каждом этапе и почему
сколько учебных групп и каких программ
сколько программ исправлено контрпримерами
support/future/parity по каждому кандидату
ACTIVE программы по разным семействам
реальные CPU ACCEPT
реально предотвращённые вызовы
точно сэкономленные входные токены
ложные разрешения и расхождения
время каждого этапа
текущий главный разрыв
```

Оценка этапа не может быть `10/10`, если его вклад ограничен только `wait` или
если широкая экономия токенов отсутствует.

## 14. Порядок реализации

1. Выделить типы `CanonicalTurnEvent`, `RuntimeView`, `TeacherView`, `CompletedTurn`.
2. Перевести адаптер Codex JSONL на эти типы без изменения runtime authority.
3. Ввести точную смысловую границу завершения хода.
4. Реализовать `ValueGraph` и `OutputGraph`.
5. Заменить `assistant_frames` новым извлечением структурных связей.
6. Подать новые примеры в существующий teacher grouping.
7. Расширить синтез существующими программами коллекций и шаблонов.
8. Заменить удаление кандидата реальным набором repair-переходов.
9. Сохранить parity cases в bounded checkpoint.
10. Ограничить очередь уведомлений и убрать повторную работу.
11. Обновить единый русский отчёт и причины отказа.
12. Выполнить одну сборку связного блока.
13. Выполнить узкие проверки затронутых контрактов.
14. Запустить composite gate.
15. Развернуть Rust-бинарники.
16. Проверить реальный живой поток, CPU ACCEPT и экономику.

## 15. Политика проверки во время реализации

- Не запускать тяжёлый полный набор после каждого изменения.
- Сначала завершить связный блок кода.
- Использовать форматирование и точечную компиляцию только при необходимости
  обнаружить ошибку типов.
- После связного блока выполнить одну release-сборку и узкие контрактные тесты.
- Перед выдачей authority обязательно выполнить `nando-live-transition-gate`.
- Для каждого длительного действия записывать фактическое время.
- Если команда превышает безопасное ожидаемое время, остановить её и сообщить,
  какой процесс и этап заняли время.

## 16. Определение завершения

### Техническое завершение

- В живом потоке автоматически появляются разные программы, а не только `wait`.
- Есть минимум `project`, `status`, `count`, `filter` и одна композиция.
- Каждая ACTIVE-программа имеет support, независимое future, parity и receipts.
- После перезапуска authority и parity остаются проверяемыми.
- Ложные разрешения и расхождения равны нулю.

### Продуктовые рубежи

```text
M1: >= 100 реальных предотвращённых вызовов и >= 1% входных токенов
M2: воспроизводимые 10-20% входных токенов на нескольких днях/сессиях
M3: >= 50% входных токенов на процессоре
```

Работа не считается завершённой на лабораторном кандидате, отчёте `PASS` или
одном ACTIVE `wait`. Конечный результат определяется только фактической долей
обычного живого трафика, независимо проверенного и исполненного на процессоре.
