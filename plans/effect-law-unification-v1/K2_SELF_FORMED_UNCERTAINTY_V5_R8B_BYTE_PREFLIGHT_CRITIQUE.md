## Verdict

The first byte-preflight draft was not sufficient for implementation. Six
defects were found before any product Rust edit. All six are repaired in the
current candidate, but the candidate remains non-authoritative until the fresh
implementation preflight returns `READY_TO_IMPLEMENT`.

## Findings And Repairs

| Severity | Finding | Why it mattered | Repair |
|---|---|---|---|
| P1 | A standalone probe Cargo manifest resolved dependencies independently of the root `Cargo.lock`. | A newer `serde` or `serde_json` could produce a compatibility baseline that was not generated by the frozen workspace. | Deleted the standalone manifest; both probes are mounted only as temporary workspace examples and run with `--locked`. |
| P1 | The first Development owner fixture descriptor used a synthetic experiment root. | The current owner correctly rejected the response because its generated experiment ID differed; accepting such a fixture would hide a broken binding. | Derive the descriptor experiment ID from `generate_self_formed_development_batch_v1` before dispatch. The failed journal remains retained. |
| P1 | The successful V2 fixture writer validated values before writing but did not reopen every final file. | A write or canonical decode defect after persistence would not have been detected. | V3 reopens all 41 files through their exact Rust types and requires byte-identical reserialization. |
| P1 | The fixture manifest stated the whole source tree was unmodified. | The tracked product diff was empty, but the temporary example was intentionally untracked; the broader statement was false. | Replaced it with separate `tracked_product_source_diff_empty=true` and `build_checkout_had_untracked_probe_mount=true` fields. |
| P1 | The first Development byte contract froze field order but not exact Rust field types. | `u32`, `u64`, `Option<String>` and plain strings can serialize differently or admit incompatible code despite identical names. | Added exact field types and numeric/option encoding for all three structs and the reconstruction tuple. |
| P1 | Root tuples had no preimplementation known-answer vectors. | An implementation and a post-hoc test could share the same mistaken tuple and still pass. | Added a paper-only mirror probe and frozen artifact, reconstruction, split and owner vectors before product implementation. |

## Remaining Claim Boundary

The fixtures and vectors prove only:

```text
current Confirm bytes are captured before implementation
the proposed Development field types and nested tuples compile
the frozen candidate tuples produce fixed known-answer roots
```

They do not prove future validators, immutable publication, restart recovery,
private custody, linked process execution, cleanup, resources or R8B scientific
success. The mirror probe deliberately uses the current canonical serializer;
it is an independent preimplementation type layout, not an independent
implementation of canonical JSON or SHA-256.

The historical Development owner fixture binds its absolute lab path through
the owner request root. It is therefore a decode/reserialize golden fixture,
not a cross-run root-equality oracle. The Confirm generator/split fixtures are
deterministic and were byte-identical between the successful V2 and V3 runs.
