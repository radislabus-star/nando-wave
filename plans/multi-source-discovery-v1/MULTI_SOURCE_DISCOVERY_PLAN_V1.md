# Nando Multi-Source Discovery Plan V1

Status: `STOP_MS0_COMPLETE / STOP_MS1_REVIEW_REQUIRED`

Date: 2026-07-24 Europe/Tallinn.

Scope: factor the current `UNEXPLORED_MULTI_SOURCE` opportunity class into
bounded, source-neutral operator-discovery work and carry the highest-value
laws through the existing proof and admission route.

This plan changes no runtime authority, admission threshold, ACTIVE package,
provider fallback, or production registry. It does not claim that every token
currently labelled `UNEXPLORED_MULTI_SOURCE` is CPU-executable.

## 1. Exact Problem

The current system has two correct but disconnected views.

```text
ordinary intent
-> CpuDecidability
-> disjoint OpportunityBoard class
-> UNEXPLORED_MULTI_SOURCE

completed relation frame
-> teacher pool
-> bounded known-grammar enumeration
-> CEGIS cohort
-> candidate operator
```

The first route sees the economic mass. The second route discovers programs.
There is no owner that turns a large unresolved opportunity class into a
ranked set of concrete discovery work items.

Therefore the system can truthfully report:

```text
UNEXPLORED_MULTI_SOURCE = 557,668,032 unique ordinary tokens
```

while the miner continues working mainly on local scalar programs already
expressible by the current candidate grammar.

## 2. Meaning Of `UNEXPLORED_MULTI_SOURCE`

The current classifier uses this class when pre-action state contains one of:

```text
multiple grounded tool observations
multiple tool-output parts
multiple structural JSON results
```

This is a coarse routing class. It means:

> More than one potential source or role is observable, but the current live
> route has not established one unique executable multi-source program.

It does not prove:

- that the examples share one law;
- that the current IR cannot express the law;
- that all 557.7 million tokens are recoverable;
- that more evidence alone will solve the case;
- that a multi-role program is necessarily required;
- that the result is deterministic.

The class can contain easy request-referenced projections, multi-value
renderers, transforms, compositions, genuinely ambiguous cases, and creative
responses.

## 3. Non-Negotiable Boundaries

1. Do not create a second miner.
2. Do not make the OpportunityBoard an authority owner.
3. Do not put teacher output or post-action atoms into runtime applicability.
4. Do not use field names, literal values, repository names, action names, or
   response text as canonical law identity.
5. Do not sum overlapping cohort `positive_tokens`.
6. Do not replace `32 + 32` with another global evidence count.
7. Do not let a candidate synthesize or validate its own verifier.
8. Do not modify ACTIVE generation in place.
9. Do not add a VM primitive until a high-marginal frozen candidate requires
   it.
10. Budget exhaustion, missing joins, ties, and incomplete search yield
    `ABSTAIN` or censored evidence.

## 5. Ownership

```text
nando-transition-serving
  emits existing hash-only opportunity events
  emits existing bounded learning-request structure
  never groups laws or grants authority

nando-operator-learning
  joins evidence by TurnIntentId
  factors source-neutral shapes
  owns the discovery work queue
  owns version spaces and candidate compilation
  cannot grant authority

nando-operator-kernel
  owns immutable multi-source contracts and versioned wire types
  contains no learner state, response schema, filesystem, or HTTP

nando-core Wave blueprint engine
  performs bounded role alignment and circuit search
  ranks candidates but cannot establish truth

nando-operator-runtime
  binds runtime roles and executes existing typed VM programs
  cannot select proof truth or grant authority

nando-operator-proof
  independently reconstructs expected roles, relations and output
  cannot reuse actor-selected values as its oracle

nando-operator-admission
  reconstructs proof, checks negatives/future/parity and issues lease

nando-gateway-control
  reads compact aggregate snapshots only
```

## 6. Reuse Before Extension

Two existing process bridges remain separate:

```text
OpportunityBridgeV1
  intent hash + token economics + class + bounded reason

LearningEvidenceBridgeV1
  TurnIntentId + request/context/capability atoms
  + optional bounded raw replay
```

`STOP-MS0` must first test whether these streams plus `RelationFrame` already
contain enough structural information to factor multi-source cases.

If they are sufficient, no bridge schema changes are allowed.

If an exact structural field is missing, extend
`LearningRequestStructureV1 -> V2`. Do not overload the economics-only
OpportunityBridge with raw payload or a second structural truth.

## 7. Learning Contracts

### 7.1 Pre-action shape

The factorizer derives a compact pre-action observation:

```text
PreActionMultiSourceShapeV1 {
    turn_intent_sha256
    session_lineage_sha256
    input_tokens
    decidability_reason
    grounded_output_count
    output_part_count
    scalar_type_histogram
    collection_cardinality_classes
    temporal_output_topology
    request_relation_atom_root
    pre_action_context_atom_root
    capability_atom_root
    provider_bound_identity
}
```

No raw value or name enters the canonical shape.

### 7.2 Completed learning fragment

Completed teacher evidence is represented separately:

```text
CompletedMultiSourceFragmentV1 {
    turn_intent_sha256
    lineage_sha256
    pre_action_shape_root
    local_structural_roles
    local_relation_fragments
    typed_program_atoms
    observed_effect_delta_root
    verifier_receipt_root
    teacher_surface_commitment
}
```

Teacher evidence may help induce a law, but the fields below must be derivable
again from pre-action state at runtime:

```text
applicability guard
role bindings
relation predicates
transform operands
composition order
```

### 7.3 Shape identity

```text
MultiSourceShapeIdV1 =
  hash(
    type/cardinality multiset,
    output temporal topology,
    request-to-source relation shape,
    capability shape,
    pre-action context relation shape
  )
```

Excluded from identity:

```text
raw field names
raw scalar values
teacher response bytes
post-action-only atoms
operator winner ID
repository/session path
```

## 8. Factorization Ladder

The 557.7 million-token class must be split in this order.

### F0. Coarse reason

```text
multiple_grounded_tool_observations
multiple_tool_output_parts
multiple_structural_results
```

### F1. Pre-action structural form

```text
one output, many scalar leaves
many outputs, one relevant latest result
many outputs, cross-output dependency
one collection plus scalar metadata
status plus value
multiple collections
mixed structured/unstructured outputs
```

### F2. Required result form

This is learned from completed fragments and cannot become runtime
applicability evidence:

```text
single-role projection
multi-role rendering
status/value branch
collection transform
cross-output composition
non-deterministic or unexplained
```

### F3. Law family

Independent lineages are grouped only when their source-neutral role and
relation topology is compatible.

```text
local names differ
local role ordinals may differ
surface renderer may differ within a bounded renderer family
effect and preserved-frame contract must agree
```

Any unresolved symmetry remains a version-space alternative.

## 10. Marginal Coverage Ledger

One intent may match several candidate laws, but its tokens can be purchased
only once.

```text
authoritative ordinary intent map
-> candidate coverage sets keyed by intent SHA-256
-> subtract ACTIVE coverage
-> deterministic marginal portfolio selection
-> aggregate rows for the control API
```

Required identities:

```text
sum disjoint opportunity classes = ordinary tokens
sum factorized multi-source shapes = UNEXPLORED_MULTI_SOURCE tokens
sum selected marginal gains <= unresolved tokens
same intent contributes to at most one selected portfolio gain
CPU gain is counted only after an admitted receipt
```

The dashboard receives aggregates, never intent lists.

## 11. Bounded Discovery Tiers

Do not search the complete rich-program cross-product at once.

### T1. Request-referenced single role

Problem:

```text
many observable values
-> request structure uniquely selects one role
-> project and render one value
```

Reuse:

```text
RequestReferencedJsonField
RequestReferencedJsonFieldOrdinal
existing scalar projection
existing renderer
```

This is the first expected high-yield tier because some current
`multiple_structural_results` cases may only require better grounding.

### T2. Multi-role renderer

```text
two or more structurally bound values
-> stable role order
-> RenderSequence
-> preserved static frame
```

No literal response may become the renderer program. Static text must satisfy
the existing transfer-bound budget and structural renderer policy.

### T3. Status plus value

```text
status role + result role
-> typed comparison
-> bounded branch
-> render selected result form
```

### T4. Collection transform

```text
collection role + predicate/value role
-> FILTER / MAP / COUNT / COMPARE
-> typed result
-> renderer
```

Add a VM primitive only when an otherwise frozen high-value version space
cannot compile without it.

### T5. Cross-output composition

```text
output A -> intermediate role
output B + intermediate role -> result
-> bounded CompositionDag
```

Each suboperator must remain independently unfoldable and verifiable.

## 12. Version Space And Grokking

Support does not use a fixed row count.

```text
observations
-> enumerate bounded semantic programs
-> quotient action-equivalent programs
-> version space
```

Outcomes:

```text
zero programs
  -> missing representation/IR or permanent ABSTAIN

one semantic program
  -> freeze candidate
  -> request independent distinguishing future

multiple programs
  -> compute the cheapest probe with maximum guaranteed split
  -> keep authority false
```

For rich circuits:

```text
CompletedMultiSourceFragmentV1
-> SurfaceFragmentBundle
-> local role canonicalization
-> competing alignments and blueprints
-> cross-plane phase coherence on independent future
-> unique complete circuit
-> crystallization
```

Wave ranks and aligns. Immutable evidence and the independent verifier decide.

The adaptive proof basis may be small:

```text
simple T1 law: potentially 1 support + 1 distinguishing future
rich ambiguous law: as many observations as the open version space requires
```

Reservoir capacity is a memory bound, not an evidence threshold.

## 13. Distinguishing Probe Contract

A probe specification describes missing evidence; it does not modify user
traffic.

```text
ProbeRequestV1 {
    shape_id
    competing_program_roots
    required_pre_action_distinction
    expected_partition_sizes
    verifier_cost
    stable_tie_break
}
```

Natural traffic matching the probe may be evaluated in shadow.

Active synthetic probes are allowed only in development isolation and cannot
become production authority or frozen future evidence.

Timeout, unavailable environment, missing join and budget exhaustion are
censored outcomes. They never become anti-centers.

## 14. `MISSING_EXTERNAL_VERIFIER` Is A Separate Queue

The 181.8 million-token verifier class must not be sent back through law
discovery merely because it is large.

```text
known or candidate effect law
-> VerifierWorkItemV1
-> independent verifier contract
-> negative controls
-> actor/verifier parity
-> admission
```

If discovery is also incomplete, the intent remains in the earlier unresolved
class until the law is established. One intent has one disjoint opportunity
class at a time.

## 22. Success Definition

The module succeeds when:

```text
large coarse opportunity class
-> disjoint source-neutral shapes
-> token-ranked discovery work
-> bounded competing programs
-> one phase-coherent executable circuit
-> independent verifier
-> immutable admitted package
-> measured new CPU receipts
```

The intelligence claim is not that the system recognized “multiple values.”
It is that several partial real surfaces caused one previously absent
multi-role program to form, transfer to a new surface, and execute with zero
false accepts and zero parity mismatches.
